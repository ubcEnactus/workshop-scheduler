## Delivered workflow

1. Create a custom-titled run with an inclusive Vancouver date window, duration, and staffing bounds. Optional order numbers are independent of identity; duplicating creates a new run.
2. Select representative classes across schools and review the exact new/existing/waived enrollment pairs before applying. Every enrolled class appears in run coverage.
3. Enter confirmed recurring weekly class blocks, effective dates, extra dates, class exclusions, and school closures. Legacy reference blocks need explicit activation. Candidate generation fits the actual session duration and preserves run-specific candidate scope.
4. Browse dated choices by week. Inspect recommended PAs separately from PAs needing workload overrides, with commitment context and lifetime totals. Review a complete class/time/PA roster before confirming dated drafts. Weekly and same-day alternatives appear only after a concrete complete temporary batch plan is found; previewing never approves exceptions. Partial plans remain visible with honest warnings.
5. Assign PAs to fixed dates. Automatic matching observes full availability, nonoverlap, one per day, and one per Monday–Friday Vancouver week. It uses deterministic bounded repair and lifetime totals as fairness. Monthly quota rows are irrelevant.
6. Show red same-day and amber weekly warnings alongside availability warnings. Manual Assign/Add records the relevant exceptions directly, without an override form, separate reason or confirmation checkbox. Touching sessions at the same school remain a hard consecutive-class block. Automatic matching still requires full coverage and its day/week limits, and real conflicts remain blocked. Existing manual/published work and saved exceptions survive reruns.
7. Publish ready sessions. Later edits can change dates, PA teams, mode/location, participant instructions, and internal notes together. Published sessions may retain a staffing deficit after a removal. Completion updates the class enrollment too.
8. Record external communication separately for each publication or participant-affecting change. Internal-only edits do not generate tasks or expose private notes/reasons to participants.
9. Review effective teacher handovers, cancel pending transfers with a recorded reason, and archive/reactivate classes only after resolving obligations. Booking follows the teacher effective on the selected date. Preserve historical host context and paginate participant history.

## Pilot boundaries

Automatic emails, PA acceptance, teacher scheduling, external calendar synchronization, travel optimization, grouped-class models, reusable content templates, and optional workload caps remain deferred by the agreed scope. Same-school “consecutive” means adjacent intervals with no gap; other separated same-day work still requires explicit admin approval. Real email and restore rehearsal remain production release gates; this deployment targets the dedicated disposable test environment only.

The 20 September production-dependency audit still reports the known `deepmerge-ts` advisory through Prisma's configuration tooling (three package entries for one advisory). Its identified use reads the repository's static Prisma configuration rather than participant input. No forced Prisma downgrade or unverified major dependency override was applied; remediation remains a production release gate in `PILOT_RUNBOOK.md`.
